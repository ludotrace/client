## Verified end-to-end

Confirmed working via manual end-to-end test or observed in production.

- **Singleton lock** — `internal/lock/lock.go`: `O_CREATE|O_EXCL` on `ludotrace.lock`, PID written into the file. On contention, reads the existing PID and checks liveness (`lock_windows.go`: `OpenProcess`+`GetExitCodeProcess`; `lock_unix.go`: `Signal(0)`); a lock left by a killed/crashed process (dead PID, or empty/unparseable — the pre-fix format) is reclaimed automatically instead of blocking forever. A lock held by a live process still returns `ErrHeld`. Fixes #26, where a non-graceful exit permanently wedged both manual relaunch and Windows autostart. Unit-tested (`lock_test.go`, 4/4: acquire/release, live-PID rejection, dead-PID reclaim, empty-file reclaim).
- **Config load + validation** — `internal/config/config.go:Load()`: TOML parse, URL validation, `filterGames` skips missing watch paths with WARN, `LUDOTRACE_CORE_URL` / `LUDOTRACE_APP_URL` env overrides applied.
- **File watcher (fsnotify, 2 s debounce)** — `internal/watcher/watcher.go`: watches WRITE+CREATE events; if events file absent at startup, watches parent directory and promotes to file watch on CREATE (`watcher.go:52-65`). Debounce timer reset on burst (`watcher.go:149-150`).
- **Startup extraction** — `internal/watcher/watcher.go:Start()`: immediately triggers `cb(gameID)` for each game whose events file exists before entering the event loop (`watcher.go:74-78`).
- **Session extraction + sidecar offset** — `internal/session/session.go:Extract()`: reads from persisted byte offset, splits on `session_start` only (session_end is opaque payload), uses custom `scanRawLines` to avoid 1-byte drift on `\r\n` Windows files (`session.go:224-234`). Offset written atomically (write-tmp, rename) via `AdvanceOffset()` only on 202.
- **Durable queue** — `internal/queue/queue.go`: JSON array flushed atomically to `queue.json` after every enqueue/dequeue/attempt-count update. Loaded on startup before watcher runs (`main.go:75-79`).
- **Auth — browser sign-in flow** — `internal/auth/auth.go:SignIn()`: ephemeral `127.0.0.1:{random-port}` loopback listener, opens `{coreURL}/auth/signin?redirect_uri=...&state=...` in system browser, receives opaque token on callback, stores via `keychain.Store`. Browser launch goes through the shared `internal/browser` package, which on Windows uses `rundll32 url.dll,FileProtocolHandler <url>` rather than `cmd /c start <url>` — the latter let cmd.exe's parser split the URL on the unquoted `&`, truncating it before `&state=` so Core rejected the sign-in with "missing state" (Windows-only; broke sign-in for every client once Core began requiring the state nonce). `SignIn()` now also logs the exact URL it hands to the OS. Validated end-to-end on a real Windows machine 2026-07-04: v0.1.1 + this fix redirects to the full sign-in URL and completes; `internal/browser` unit test asserts the URL survives as a single argv entry and never routes through cmd.exe.
- **Auth — keychain chain store** — `internal/keychain/keychain.go:chainStore`: OS keychain (`zalando/go-keyring`) → DPAPI-encrypted file fallback on Windows (`fallback_windows.go`, `crypt32.dll` via syscall) → in-memory only on non-Windows without Secret Service. Three distinct outcomes: `nil` (OS keychain), `ErrSignedInDegraded` (DPAPI fallback used), `ErrSignedInNotPersisted` (in-memory only). Windows Credential Manager full → DPAPI fallback path confirmed shipped. `chainStore` save/load/delete precedence and the full-primary → fallback path unit-tested against fake `Store`s (`keychain_test.go`) — the real OS keychain and Windows DPAPI backends aren't exercised (no Secret Service / DPAPI in CI), only the chaining logic around them.
- **Auth — opaque token → short-lived JWT** — `internal/auth/auth.go:fetchJWT()`: `POST {coreURL}/v1/auth/token` with `Authorization: Bearer <opaque>`, caches JWT + expiry, single-flight via `refreshMu`, proactive refresh 10 s before expiry. 401 from Core clears keychain and returns `ErrTokenRevoked`. Refresh-on-expiry, cache-hit, and revoked-token (no-infinite-retry) paths unit-tested against an `httptest` Core (`auth_test.go`).
- **Auth — sign out** — `internal/auth/auth.go:SignOut()`: best-effort `DELETE /v1/auth/token`, clears in-memory JWT + opaque token, deletes keychain entry.
- **Upload — gzip + streaming multipart POST** — `internal/uploader/uploader.go:doUpload()`: pipes file through `gzip.Writer` into multipart part without buffering full payload in memory. Three attempts with delays [0, 200 ms, 400 ms] on transient errors; permanent 4xx returns immediately.
- **Upload response handling** — `internal/uploader/uploader.go`: 202 → returns `job_id`; 401 → `ErrUnauthorized`; 413 → `ErrFileTooLarge`; 429 → `ErrLimitReached`; 400 → `ErrBadRequest{Reason}`; 5xx/network → retried then `ErrTransient`.
- **Upload worker — post-202 cleanup** — `cmd/ludotrace/main.go:runUploadWorker()`: on 202, calls `ext.AdvanceOffset(item.EndOffset)`, `os.Remove(item.TmpPath)`, `q.Remove(item.TmpPath)` in that order.
- **Tray — 6 states** — `internal/tray/tray.go`: `StateIdle`, `StateUploading`, `StateError`, `StateLimitReached`, `StateNotAuth`, `StateNoGames`. Icons embedded via `//go:embed` (`icon.ico`, `icon_error.ico`, `icon_uploading.ico`). Menu items pre-created and show/hidden per state (systray does not support dynamic rebuild).
- **Tray — Open Dashboard** — `internal/tray/tray.go:eventLoop()`: opens `t.appURL` in system browser via `open`/`cmd /c start`/`xdg-open`.
- **Tray — Manage Games** — `internal/tray/tray.go:eventLoop()`: opens `config.FilePath()` in OS default app (same `openBrowser` helper).
- **Tray — Sign In / Sign Out** — `internal/tray/tray.go:eventLoop()`: `auth.SignIn(ctx)` / `auth.SignOut(ctx)` wired; degraded/not-persisted states surfaced to user. A genuine sign-in failure/timeout (the `default:` branch — error, 5-min timeout, or ctx cancellation) now returns to `StateNotAuth` via `SetSignInFailed()` with the reason on the status line (Sign In / Quit only), instead of `SetError`→`StateError`, which wrongly rendered the full authenticated menu for a user who never signed in (#48). The `ErrSignedInNotPersisted` branch (in-memory sign-in *success*) is unchanged and still shows the authenticated-with-warning state.
- **Limit reached (429)** — `cmd/ludotrace/main.go:runUploadWorker()`: sets `StateLimitReached`, increments attempts, then waits before retry. When Core sends no usable `Retry-After` header the wait is the fixed 60 s fallback (`limitReachedDefaultWait`) — this fallback path is the verified behavior. Honoring a server-provided `Retry-After` is new (see "Implemented, not yet validated").
- **Auto-update — client mechanism** — `internal/version/version.go`: `Version` injected via ldflags. `internal/updater/updater.go`: `Check()` fetches the manifest, compares semver, returns an `*Update` only when strictly newer and skips entirely on dev/dirty/untagged builds; `Stage()` streams + SHA-256-verifies + atomically stages `pending_update[.exe]` and writes a `pending_update.json` version sidecar. `cmd/ludotrace/main.go`: `--check-update` one-shot; `--finish-update` self-install; `runUpdateWorker` checks on startup + server-controlled interval; startup is version-aware — re-surfaces "Restart to Update" only when the staged version is newer, else clears the stale leftover (fixes the Windows self-delete-fails → false re-prompt). `internal/tray/tray.go`: `NotifyUpdateReady()` shows real version + "Restart to Update". Validated end-to-end on Windows via `scripts/test-autoupdate.sh` (download / skip-on-dev / apply / stale-cleanup, 9/9) and `go test ./internal/updater` (httptest-driven Check/Stage/reconcile).
- **Auto-update — release pipeline** — `.github/workflows/release.yml`: on a `v*` tag, a 2-runner matrix builds all 4 platforms (ubuntu → Windows pure-Go + Linux CGO/GTK; `macos-latest` → darwin x64 + arm64 with `CGO_ENABLED=1`), computes SHA-256 (`shasum`), creates a GitHub Release, and pushes binaries + `client/version.json` to the site repo via `SITE_DEPLOY_TOKEN`. First ran on **`v0.1.0` (2026-06-29)**: all jobs green; site commit landed all 4 binaries + manifest; live manifest serves **HTTP 200** at `https://ludotrace.com/client/version.json` (apex CNAME → `ludotrace.github.io`, DNS-only) with SHA-256 matching the published binaries byte-for-byte. `ci.yml` `build-macos` / `build-linux` jobs guard the non-cross-compilable platform builds on every push. Mac targets require a macOS host (systray needs CGO/Cocoa; Go disables CGO when GOARCH ≠ host arch). Linux needs `libayatana-appindicator3-dev` on Ubuntu 24.04.
- **Auto-start on login** — `internal/autostart/autostart_windows.go`: writes `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run` with the quoted executable path on every startup (idempotent via `strings.EqualFold` comparison). Called from `cmd/ludotrace/main.go` immediately after the singleton lock is acquired. Non-Windows platforms get a no-op stub (`autostart_other.go`). Confirmed on a real Windows machine: `ludotrace.exe` resumed correctly following a restart (2026-06-30).
- **Add Game dialog** — `internal/steam/steam.go` + `steam_windows.go`/`steam_other.go`: Windows registry (`SteamPath`) + hand-parsed `libraryfolders.vdf` discovery (unescapes `\"` and `\\`, propagates scan errors instead of discarding them), matched against `steam.Registry` (`stardew` only — Steam-folder auto-discovery is unchanged and scoped to games whose watch_path *is* their Steam install dir). `internal/watcher/watcher.go:AddGame()`: RWMutex-guarded, stats `watch_path` before registering (rejects a vanished/non-directory path), idempotent per `game_id`, reuses `New()`'s per-game setup via a shared `setupGameWatch` helper — a game is watched live, no restart. `internal/tray/tray.go`: `addGame`/`addGameNG` clicks wired to an injected handler (`SetAddGameHandler`) behind a `CompareAndSwap` re-entrancy guard (`triggerAddGame`). `cmd/ludotrace/main.go`: composes discovery → dedupe → `sqweek/dialog` folder picker (recognized-folder resolution via `steam.Registry`, or an unrecognized-folder Yes/No prompt sourced from `internal/knowngames.List` — Core's `GET /v1/games`, cached to `known_games.json` for offline fallback, client#29) → extractor registered → `w.AddGame` (validates path) → `config.AppendGame` (extractor registered *before* the watch goes live) → `t.SetHasGames(true)`/`SetState(StateIdle)`. For a Core-sourced (non-Steam-registry) game, `watch_path` is the folder the user picked directly and `events_file` is derived from the `lt_<game_id>_events.jsonl` convention (`steam.EventsFileName`) — there is no per-game default-path table, since Core's `/v1/games` carries only `game_id`+`name`. **Outcome is surfaced as a native modal dialog** (`notifyGameAdded`/`notifyGameInfo`/`notifyGameError` via `sqweek/dialog`) — the earlier tray-menu-item confirmation (`NotifyGameAdded`/`addedLoop`) was invisible in practice, because clicking a tray item closes the menu, so the confirmation was never seen; that machinery is removed. `internal/steam`, `internal/watcher.AddGame`, and `internal/knowngames` (fetch → cache write, fallback-to-cache on fetch error, error when neither available) unit-tested (VDF parsing incl. escaped-quote case, folder matching, dedupe, concurrent `AddGame` under `-race`, missing/non-directory/vanished-path rejection, idempotent re-add). **Validated end-to-end on a real Windows machine:** Stardew auto-discovery via Steam library scan (2026-07-01, `fallout4`-only config → picked up Stardew, correct `[[games]]` entry, live watch, "Stardew Valley added" modal, `ludotrace.log` confirmed). **Fallout 4 via the Core-sourced unrecognized-folder path (2026-07-04, client#29):** pointed the picker at FO4's real `Documents\My Games\Fallout4` events folder (not Steam-derivable), prompted "Add it as Fallout 4?" from the live `GET /v1/games` list, added correctly with no `config.toml` hand-editing.
- **File logging** — `cmd/ludotrace/main.go:openLogFile`/`tolerantTee`: `slog` is teed to `%APPDATA%\ludotrace\ludotrace.log` (created early, before other startup work) *and* stderr. A GUI-subsystem build (`-H=windowsgui`) has an invalid `os.Stderr`, so a plain `io.MultiWriter(os.Stderr, f)` aborts on stderr's error and never writes the file — `tolerantTee` writes every writer regardless, so a dead stderr can't suppress the log. Single-generation rotation at 5 MiB (`ludotrace.log.old`); a log-open failure is non-fatal (falls back to stderr-only). Confirmed on a real Windows machine (2026-07-01): the file is created and both the startup line and the `game added` line land in it. This is the first field-diagnosable logging the client has had — a windowless tray process previously discarded every log line.
- **Resource-footprint tests (#13)** — `go.uber.org/goleak` wraps `TestMain` in every test package (`*_leak_test.go`); `go test ./...` fails on a goroutine leak. `runUploadWorker`'s backoff/retry branches (`cmd/ludotrace/main.go`) now share one `time.NewTimer`+`Reset` instead of a fresh `time.After` per branch, so rapid repeated errors no longer accumulate timers in the runtime heap. `BenchmarkExtract` (`internal/session`) confirms `Extract()` cost is flat (~18µs) across a 1 MB and 10 MB events file — offset-seek, not whole-file scan. `BenchmarkQueueFlush` (`internal/queue`) confirms a 50-item queue flush is sub-millisecond (~0.5ms). `scripts/measure-idle.sh` runs the built binary headless (Linux, via Xvfb + a D-Bus session) for 60 s with no games configured and fails if peak RSS or goroutine count (via a `SIGQUIT` dump) exceed budget. Measured baseline: ~31 MB RSS, 18 goroutines — of which ~13 goroutines / ~30 MB are fixed cost (Go runtime, systray's native loop, stdlib `signal.NotifyContext`, the D-Bus connection `getlantern/systray`'s Linux appindicator backend opens, fsnotify's inotify reader) before any of the client's own long-running loops start. The tray's three separate loops (`stateLoop`/`updateLoop`/`clickLoop`) were consolidated into one `eventLoop` (20→18 goroutines), a zero-behavior-change cut; no further reduction is possible without dropping functionality, so the script's budget (35 MB / 22 goroutines) tracks the real floor with modest slack rather than the original design-time guess of 30 MB / 15.

## Implemented, not yet validated

Code exists and is wired up; not confirmed working under real conditions.
- **Bounded upload queue — age-based drop-oldest + newest-first upload (#60)** — `internal/queue/queue.go`: `Item` gains a persisted `CapturedAt` (set at enqueue in `internal/session/session.go`, so ordering and eviction survive a restart from `queue.json` rather than relying on volatile file mtimes; a legacy `queue.json` with no timestamp is backfilled from temp-file mtime on load). `EvictExpired(maxAge, now)` drops every item whose age strictly exceeds the threshold — oldest-first — and returns them so the caller cleans up temp files; the boundary is inclusive-keep (an item at exactly `maxAge` stays). `PeekNewest()` selects the most-recently-captured item, deliberately distinct from eviction order (evict oldest tail, upload newest head) so a chronically over-quota player spends quota on the session they just played. `internal/config/config.go`: `QUEUE_MAX_AGE_DAYS` env var (default 30 = 2× Core's `UPLOAD_WINDOW_DAYS`; invalid/≤0 falls back to default). `cmd/ludotrace/main.go:runUploadWorker`: evicts at the top of each loop iteration, then selects via `PeekNewest` instead of `Peek`; a drop logs a WARN line ("dropped old sessions, over quota too long", count) and calls `tray.NotifyDropped`. `internal/tray/tray.go`: `NotifyDropped(count)` accumulates the count and shows it on the `StateLimitReached` status line ("Free upload limit reached — N old sessions dropped"), cleared by `ResetDropped()` on the next successful upload. Newest-first does not fight existing per-item backoff/attempt tracking (`UpdateAttempts` is keyed by `TmpPath`; backoff is global, so a failing newest item still backs off before retry). Unit-tested: eviction count/oldest-first order/threshold boundary/persisted-flush, newest-first selection on a mixed-age queue, both orderings re-derived after a simulated restart (reload from `queue.json`), legacy-timestamp backfill (`internal/queue/queue_bounded_test.go`); env default/override/invalid-fallback/missing-file (`internal/config/config_maxage_test.go`); drop-notification count accumulation + message rendering (`internal/tray/tray_dropped_test.go`, runs in CI where GTK is present). **Not yet validated live:** the drop surfacing on a real tray and the end-to-end over-quota behaviour on a machine are unconfirmed; the queue/config logic is exercised only by unit tests.
- **Honor Core's Retry-After on 429 (#59)** — `internal/uploader/uploader.go`: on a 429 the response now returns `*LimitReachedError` (wraps the `ErrLimitReached` sentinel, so existing `errors.Is` checks are unchanged) carrying an optional `RetryAfter time.Duration` parsed from the RFC 7231 `Retry-After` header. `parseRetryAfter` handles both defined forms — delta-seconds (e.g. `Retry-After: 43200`) via `strconv.Atoi`, and HTTP-date via `http.ParseTime` — and treats empty/non-positive/past-dated/unparseable values as "no hint" (zero, meaning fall back). `cmd/ludotrace/main.go:limitReachedWait` honors a present hint clamped to [5 s, 24 h] and otherwise uses the fixed 60 s fallback; the 24 h cap bounds a bogus/huge value so the worker re-checks at least daily. Header parsing (both forms, malformed, missing), the 429→`LimitReachedError` round-trip, and the clamp/fallback decision are unit-tested (`uploader_test.go`, `cmd/ludotrace/main_test.go`). `ludotrace/core#66` (the header itself) has merged, so the code-level dependency is satisfied — an older Core still exercises the verified 60 s fallback path. **Not yet validated live:** no confirmed end-to-end run against a deployed Core actually emitting the header. The `runUploadWorker` loop wiring is not exercised by a unit test (the tray/systray cgo build is untestable off a GTK host); the decision helper it calls is.
- **Orphan / inactivity flush** — `internal/session/session.go:175-179`: if the events file `modTime` is more than `orphanThreshold` (10 minutes — code is authoritative; a 30-min drift is tracked as PRD §10 item 17, MVP-blocking) old and a session is open, it is flushed and enqueued. Correct by inspection but never observed triggering in the wild.
- **Graceful shutdown** — `cmd/ludotrace/main.go:88-131`: `signal.NotifyContext` for `SIGINT`/`SIGTERM`; ctx cancellation stops the watcher (`watcher.go:Start()` returns on `ctx.Done()`), upload worker exits its loop, and a goroutine calls `t.Quit()` to unblock `systray.Run`. The in-flight upload is not explicitly waited on — the worker loop exits on `ctx.Done()` between retries, not after the current HTTP call completes. Not stress-tested; behavior under kill-during-upload is unverified.
- **Transient failure backoff + StateQueued (offline handling)** — `cmd/ludotrace/main.go:runUploadWorker`: on `ErrTransient`/5xx the worker calls `t.SetQueued(...)` (not `SetError`) and sleeps an escalating backoff `30 s → 1 m → 5 m → 15 m → 30 m (cap)` (`cmd/ludotrace/backoff.go`), reset on any success or on "Retry Now". Permanent failures (413/400) still drop the item and go to `StateError`. The tray gains `StateQueued` (`internal/tray/tray.go`) — normal (non-error) icon, status line "N sessions queued — retrying in Xm", and a **Retry Now** menu item that signals the worker via `Tray.RetryCh()` to break the sleep and reset backoff immediately. Pure backoff/message helpers unit-tested (`backoff_test.go`, 3/3). Not yet validated against a real outage on a live machine (#4).
- **Launch heartbeat splash (#51)** — `internal/splash/`: on an interactive (bare-args, double-click) launch, flashes the org hero heartbeat mark as a borderless, centred, top-most `WS_POPUP` window for one 2x heartbeat cycle (~2.1s), then auto-dismisses — the only "it started" feedback a windowless `-H=windowsgui` build gives. `splash.Show(DecideLaunch(os.Args))` is called in `cmd/ludotrace/main.go` **before** `lock.Acquire`, so a repeat double-click that exits early on `ErrHeld` still flashes (the lock-held path calls `splashHandle.Wait()` before exiting). Suppressed on every non-interactive launch: login autostart now writes `"exe" --autostart` to the Run key (`internal/autostart/autostart_windows.go`, `EqualFold` idempotency updated to match), and `--finish-update`/`--check-update`/any-other-args are non-interactive. Window is pure-Go raw Win32 syscall (CGO-free, matching the client's Windows build) in `splash_windows.go`; `splash_other.go` is a no-op stub (macOS/Linux need Cocoa/GTK — follow-up). Motion is a uniform 2x time-scale of the site's locked 4.2s heartbeat (same keyframe proportions, half the duration — not a re-choreograph); the site's `--heartbeat-t: 4.2s` is unchanged. Frames are pre-rendered PNGs baked from the canonical avatar geometry by a pure-Go generator (`internal/splash/gen/main.go`, `go:generate`) and embedded via `//go:embed` (mirrors the tray icons), decoded to top-down BGRA DIBs and blitted with `StretchDIBits`. Non-blocking and non-fatal (a creation failure is logged and swallowed, never blocks tray init); the message-loop goroutine and all resources (brush, class, DIBs) release on close, so goleak stays green. Launch-mode decision logic unit-tested (`mode_test.go`, 9 arg combos + non-blocking suppressed path) without opening a window; window code verified only via `GOOS=windows` cross-build (`-H=windowsgui`). **Not yet run on a real Windows machine** — the window rendering, centring, top-most behaviour, and 2.1s auto-dismiss are unvalidated live; the frame art is real (renders correctly as PNGs) but has not been seen on-screen.
